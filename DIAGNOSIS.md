# Web startup/loading-screen diagnosis

## Findings

| Hypothesis | Test/evidence | Result | Decision |
|---|---|---|---|
| Google CanvasKit CDN is unreachable from this machine | PowerShell GET to the unversioned `https://www.gstatic.com/flutter-canvaskit/canvaskit.js`, `https://fonts.gstatic.com/`, and `https://fonts.googleapis.com/`; requests completed in 890 ms, 467 ms, and 619 ms respectively | All returned HTTP 404. These root/unversioned paths are not valid assets; this proves DNS/TLS/HTTP reachability only, not reachability of the user's versioned CanvasKit URL. The actual URL/hash was not included in the report. | CDN reachability for the reported exact resource remains **not proven**. |
| The app's CSP blocks the reported CDN script | `web/index.html` declared `script-src 'self' ...` with no `www.gstatic.com` origin. The reported resource is a dynamic module from `www.gstatic.com`. | The page policy does not authorize that external script origin. A CDN-enabled run can therefore fail even when opening the URL directly in Chrome works. No user-browser CSP console message was provided. | Treat this as a concrete configuration defect and avoid the CDN for app builds. |
| Flutter supports a local web-resources build | `flutter build web --help` and `flutter run --help` on Flutter 3.44.1 list `--[no-]web-resources-cdn`. | Flag exists for both commands. | Use `--no-web-resources-cdn` in deployments and web-server development. |
| Flutter release assets are local with the no-CDN setting | Build with `flutter build web --release --no-web-resources-cdn`; inspect `build/web/canvaskit` and run `dart run tool/verify_no_web_cdn.dart`. | Build succeeded; the generated bootstrap sets `useLocalCanvasKit=true`, and local CanvasKit JS/WASM assets exist. The generic Flutter loader retains an inactive CDN fallback string, so the verifier checks effective configuration and app assets rather than reporting that generic fallback as an active CDN dependency. | Keep a build verification script in CI and deployment. |
| The custom splash can remain forever after a bootstrap failure | Inspected `web/index.html`: it depended on `flutter-first-frame`, while the actual Flutter bootstrap was generated and no explicit failure or slow-start path existed. | A failed CanvasKit import, JS bootstrap, or preference initialization could leave the custom splash indefinitely. | Use `onEntrypointLoaded`, display the error after bootstrap failure, and show a bilingual 25-second watchdog with Reload. |
| Preference initialization can wait forever | `main()` awaited `openPreferences()`. `ResilientPreferencesStore` caught I/O exceptions but did not time out delegate calls. | A plugin call that never completes is not caught by a catch block. | Cap preference-platform operations at five seconds and show a startup error if the 12-second startup bound is exceeded. |
| Guarded startup zone prevents debug startup | In `flutter run -d web-server`, browser console reported Flutter's `Zone mismatch` assertion at `runApp`; the splash remained. | `WidgetsFlutterBinding.ensureInitialized()` ran before `runZonedGuarded`, while `runApp()` ran inside its zone. After moving binding initialization and global handlers into the guarded callback, a fresh debug run logged through `runApp` and loaded `/onboarding`. | Keep binding initialization and `runApp` in the same guarded zone. |
| Router redirect loop | Inspected the redirect function and existing route tests; it stabilizes signed-out users on `/login` and signed-in users on the requested path or `/products`. | No startup redirect loop was identified. A route test was added/retained for deep-link return and unknown routes. | No router change required for this loading issue. |
| Service worker serves stale code | Release bundles include a service worker; debug serving defaults do not require it. | No stale-cache evidence from the affected browser was available. | Document clearing Chrome site data and hard-refresh. |
| Release and debug apps render in browsers | Served release output on port 8081 and inspected it with browser automation; ran the debug server on 8080 and inspected its startup logs and screen. Also captured a headless Edge DOM and screenshot with GPU enabled. | Release browser: title `Products | Jatoi Bin Trader`, one `<flutter-view>` and `<flt-glass-pane>`, no loading-splash element, and no browser console errors. Debug browser: startup logs reached `runApp`, then navigated to onboarding. Headless Edge with GPU: Flutter host present, splash removed, title `Welcome | Jatoi Bin Trader`, screenshot rendered onboarding. Headless with `--disable-gpu` instead reached the watchdog; Chrome CLI reused an existing browser session. | Browser smoke test passed with GPU enabled. Do not use `--disable-gpu` for this CanvasKit smoke test. User's actual browser/network remains untested. |

## Changes and verification log

1. Hypothesis: a CDN CanvasKit import can be rejected by the current self-only `script-src`; independent CDN access is also uncertain. Test: inspect CSP and Flutter 3.44.1 help; result: external `www.gstatic.com` is not permitted and the explicit no-CDN flag exists. Decision: use local web resources for deploy/debug commands; prove build output with `tool/verify_no_web_cdn.dart`.
2. Hypothesis: a bootstrap or storage failure can leave the splash indefinitely. Test: inspect `main()` and HTML startup hooks; result: one unbounded `await openPreferences()` and no timeout/error UI. Decision: bound preference I/O, install Flutter/Dart global error reporting, use the supported bootstrap callback, and add a bilingual error/watchdog screen.
3. Hypothesis: browser cache or router is the cause. Test: inspect router redirects and current service-worker setup; result: no redirect loop found; stale cache cannot be established without the affected browser profile. Decision: leave route/business behavior alone and document Clear site data / hard refresh.
4. Hypothesis: local CanvasKit avoids the reported external import. Test: final `flutter build web --release --no-web-resources-cdn` succeeded; bootstrap config sets `useLocalCanvasKit=true`; local CanvasKit JS/WASM assets exist; `dart run tool/verify_no_web_cdn.dart` passed. The effective build does not request the CDN, although the generic loader implementation retains its unused default fallback string.
5. Flutter analyze/test: passed after the final Dart change (`flutter analyze`: no issues; `flutter test`: all 33 passed). Tests print expected fallback-storage diagnostics and the existing Helvetica Unicode warning from PDF generation. `flutter clean` succeeded; online `flutter pub get` failed with a Windows symlink/Developer Mode message, then `flutter pub get --offline` succeeded. Final no-CDN release build and local browser smoke tests passed. Android/Windows builds were not run; doctor reports the Android SDK path-with-spaces warning and missing Visual Studio C++ workload.
6. Headless/browser specifics: isolated headless Edge with GPU acceleration rendered the onboarding screen and contained `<flutter-view>`/`<flt-glass-pane>`. Disabling GPU caused the watchdog to appear; headless Chrome was not a usable test here because it handed the invocation to an existing browser session. Normal integrated-browser release and debug checks passed. A debug onboarding screenshot at a short viewport showed a 41-pixel bottom overflow; screen/layout changes are outside this startup-only fix and this issue remains open.

## Root-cause assessment

The reported exact runtime cause on the user's PC is **not proven** because the failing versioned URL, its browser console network/CSP details, proxy/VPN configuration, and browser profile are unavailable. Two concrete local defects were found and fixed: the page CSP did not allow the reported Google script origin, and debug startup initialized Flutter bindings outside the zone used by `runApp`. The no-CDN build removes the effective external CanvasKit dependency; the zone correction fixes the debug assertion. Local release/debug browser smoke tests passed after the fix, but cannot substitute for testing the affected PC.
